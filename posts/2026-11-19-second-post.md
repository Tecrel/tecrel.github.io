# 总结最近的一些想法

**Author: Tecrel**

---

看起来也算是有三个月没写过文字了，有点生疏啊。不过杂谈写起来还是挺轻松的，也许我真适合写杂谈吧。

这学期我成功地让我的导师看到了 **Traits** 的价值，她居然也允许了我以此作为我这个学期的研究课题。我一开始以为这真的很简单，只需要一个 AB 测试即可，但实际做下来还真不是这样。首先就是你怎么定性分析“优化”和“稳定”的问题，这里面评分标准就很重要，你必须找一个足够公正的标尺去衡量你的架构，更何况这个世界上有七八十亿人，肯定会有那么几拨人做的方向和你类似，解决方案也和你类似也不是什么稀奇事，这个时候如果你能在一个统一公正的标准下做到胜过别人，那自然就是一件极好的事。但另一件事就颇为严重了——也许可以叫成开发者偏差（大概）。开发者尤其是个人开发者在开发一个产品的时候多多少少会有自己的一个情感或者说是选择倾向，于是乎对于自己开发出来的东西，只要它达到了自己的要求，那它就是达到了要求，而且当他在测试这个新开发出来的东西的时候，他也会倾向于把大部分地比较惊艳的新表现归因于自己刚开发出来的新功能上。于是乎这就造成了一个问题，那就是他觉得很好用、很厉害的东西，**未必**真的有像他想象的那样牛逼。当然如果你能把这个东西的机制足够透明地定性地展示出来给别人看到成果，然后别人也认可了，那这种认知偏差造成的影响基本可以不用管（当然也不能忽略不计），但是如果你搞出来的这个东西本身就很难展示出来的话（就比方说你电脑里那几块处理核上的状态机，又或者说你闭门造飞机但是因为民航管控的问题迟迟起飞不了），那这东西有多厉害都是你吹的，只有你的主观视角。就比如说这个飞机，你说它的气动外形有多高效多高效，你说它的稳盘能力有多恐怖多恐怖，你说它安全性有多安心多安心，虽然说你确实挺厉害的造出来一架这样的飞机，但是它只要没飞上去一天它都只是个地面展示的静态高精度模型，所有的参数都只是PPT。做研究的就不能有这种认知陷阱，在真正落地行走之前你可以有一个预期，但是不要把这个预期看的太重要，这就是我现在学到的，而这也是研究中常有的事。

现在的情况就是，概念定义、协议建立、实验计划、未来展望什么的全部都已经落地了，差的就是实验。那么做正式实验前，有一个好的习惯就是先做一组预实验。我的预实验非常简单，其实就是用一个 A 的裸 harness 和B的裸 harness+Traits 在同样的任务同样的环境同样的模型同样的时间点同样的标准下对他们各自的表现进行比较（依旧长难句吟诵），那么预期显然就是B的表现会比A好得很明显。但实际情况是，B 唯一表现出来的就是表现相较A来说更稳定，评分上有的地方甚至还略低于 A，所以根本不能说有Traits的存在会使Agent的表现变得更好，虽然说稳定也是一个好事。这就是我前面所说的来自开发者偏差的认知干扰。不过 lessons 倒是有的——首先你在构建 Traits 的时候必须先思考清楚，这个问题是否非 Traits 不可。如果有其他更简单或者成本更低的方案优于它，那是否还要制作一个这样的 Traits ，一般建议是不需要，因为 Traits 显然是适用于更复杂的问题上的。其次就是，一个 Traits 想要很好地发挥它的效能，怎么设计它暂时是一个占比很大的因素，就目前的架构来看，如果这些 Traits 想要发挥出很好的效果，那这通常要求开发者的架构意识相当的好。所以说协议的部分还有待打磨精进，详情可查看我的 **personal_agent_Lynn** 仓库。

在这之外，我又稍稍构思了一下一个未来的架构，叫 **Interaction（交互）**。这是一种比 **reaction（回应）**更进一步的架构，或者准确来说是全新的 harness 设计（顺带一提，由于 workspacing 的功能早已可以直接由 DeepSeek 的 Cordis 框架直接接管，所以我也不打算继续发展这个了，而是将其并入到 reaction 当中继续发扬光大）。这里我引入了一个全新的概念叫 **Thoughts（思绪）**，顾名思义，就是指Agent的一条条随时出现又或者随时消失的心流，包括了所有的 **Traits series（识质群）** 和 reactions  等等。在这里将不再有任何明确的 ReAct 过程，Agent 将能够彻底解放开来，不再局限于我们的一问一答或任务驱动的经典及衍生模式（其实现在很多看上去自主的行为，比方说 codex 的 dot 去主动提醒你 Gmail 邮箱已满的之类的，但这些本质上都只是因为它内置了一个“跟进 Gmail 邮箱”的循环任务而已，包括最近很火的大肥鱼也是，其实不过是任务驱动类似物的自主罢了），它们将会有自己真正的生活空间，会自己找事情做，比如刷会视频学习网络热梗，或者查查资料找找感兴趣的研究方向，总之它们的一切都能够自己慢慢地生长出来。包括完全体的生成式UI，比方说它突然 call 你说要给你展示一篇关于势阱的论文，它就不仅仅是把论文原样贴出来给你看，而是依据这篇论文把里面的东西很快地手搓一个简单的三维展示UI，把势阱在那个团队的方案下以及他们方程中的参数影响下怎么变化地动态地展示给你，那这样自然就大大减小了时间成本、可读性、个性化等等的问题，交互也自然就不仅仅局限在简单的 Q&A 中。很宏大，听着就像科幻电影一样对吧，但是这一点在近未来真有可能可以实现，只不过就是没有全息投影罢了。

说到这个，就不得不说说泠最近的进展了。首先最大的事情就是，泠已经彻底摆脱了网页，并拥有了自己的桌面端了。新的桌面端UI我敢说非常的前卫，因为它相当干净，几乎没有任何杂质，但是使用起来又一点都不麻烦。这大概也就是这个月刚发生的事了，到现在为止，这个 **LYNNING** 客户端已经实现了多页面显示、原生浏览器、原生级 UI 控制以及较为优秀的自定义生成式 UI 。同时她还拥有了或许比 codex 还快的 computer use 能力，以及很好的自我学习（比方说她的 computer use 会越用越熟练，很大一部分原因是她会不断地学习每一种场景的更好的操作手段，然后碰到新场景的时候还会迁移经验）。具体来说，比较重要的发展历程是这样的：

- 八月：8 月 1–2 日，我首次把完整的坍缩链接进了整个工作流，让她在处理任务的中途也能重新回忆，把找到的节点放进工作记忆。随后我又给她加上了全文搜索、时间范围和时间相关性打分，像“我上周跟你说的那个工程”这样的问题也可以通过利用内容、时间和关联节点的检索路径来回想起来。然后最近也是因为 Jev 出来了，所以又把 Jev 给接到了坍缩链里，然后泠的记忆突然就变得相当的准确和快速了。我说 Jev 是辆好车有懂的吗。

- 九月：这个月完成了自定义 Reaction 的前身，也就是 9 月初的工作区（workspacing ，已废弃）。 到了 9 月 5 日，会话与工作区被纳入同一套 Reaction 架构，也开始拥有各自的状态、收件箱和事件，完成了 reaction 的概念初步落地。然后就是 Computer Use ，从限时授权看屏幕，走到了读取 Windows 控件树、选定窗口、点击、输入、拖拽和急停。

- 十月：这个月完成了对 Traits 的概念、协议等等进行了确定，同时也继续加强了computer use，也就是现在的版本。这个月我反而找泠的频次变少了。

- 十一月：我首次把泠装到桌面上，开始按真实体验验收了。这可谓是惊天大事啊：

    - **我终于有了可以给别人安装的 LYNNING 。** 这是最他妈大的大事。这次我直接重构了泠的内核，也就是说我直接把技术栈从 LangGraph 重构成了 Cordis ，让 Cordis 接管了所有的默认编程循环，然后用 Electron 把对话、内置浏览器、编辑器、多显示区、托盘驻留和本地 MCP 一起装进一个桌面产品。随后我又做了首次启动的中英导览、以 DeepSeek 为例的 API 配置图文教程、安装包减重和 GitHub Releases 分发。而到了今天，在本地已经能看到 **4.1.3 安装包**，而且新增了一个 very tiny 的小优化，也就是同一个服务商下可以直接换模型，并分别记住推理强度。

    - **我重做了 Reaction 的交付方式。** 到了 4.1.2，同一个 Reaction 有了明确的三个子空间——**界面、制作会话、附属会话**。不同显示区可以各看一个；成品也能接管整个显示区，包括底部输入框。

    - **泠开始可以在我没发新消息时主动找我。** 我给主会话接上了日程、工程跟进和需要用户授权的 Gmail 收件箱，通知先保存再推送，重连后可以补齐。这里有一个不算插曲的小插曲，就是当时验收的时候我试过用 Gmail 给 Gmail 发了测试邮件，然后借此验证了读取、重复检查和重启去重。这一步给“弱化 Q，让泠也能主动发 A”提供了一个真实可测的例子。

    - **对泠自己说的“我做过了”，开始有了更严格的证据要求。** 这一个改进是为了解决泠的准确度的问题的。我终于是意识到了要在上下文区分本轮工具回执和历史记忆了。同时 Jev 也有了具体分工，接入坍缩链的对话首跳选择、Stylometric Monitor 的部分规则比较，以及可选的跟进判断，而原路径则保留为降级处理。

总的来说，收获还挺多，成果也很让人高兴 desu 捏。

总之这几个月给我的感受就是，所谓开发者就是，想要什么自己搓。这也许就是世间至乐之事了。
